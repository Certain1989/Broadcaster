# EPG and SQLite storage: operations and recovery

Broadcaster uses a **private application data directory**, normally `$XDG_DATA_HOME/broadcaster/` (usually `~/.local/share/broadcaster/` for a non-Flatpak install). For a user Flatpak install the corresponding path is commonly `~/.var/app/io.github.Certain1989.Broadcaster/data/broadcaster/`. The current SQLite database is named `broadcaster-iptv.sqlite3`. Paths can differ with environment and installation type. Do not paste full filesystem paths or playlist/guide URLs into public support reports.

## Historical migration recovery copies

When Broadcaster upgrades an existing database to a newer schema, it deliberately preserves a separately reopenable recovery copy alongside the original database. Its name resembles `.broadcaster-iptv.sqlite3-v4-recovery-<UUID>.sqlite3` (the `v` number identifies the *previous* schema version). The private directory is owner-only on Unix, and recovery copies are created with file mode `0600`. These are **application-created historical migration snapshots**, not user-selected exports, active databases, or the temporary backup/import transaction files used by the database import/restore feature.

A historical copy can still contain old playlist addresses, authentication tokens and guide/source metadata, **even if those entries were subsequently deleted from the active database**. Protect copies and backups of this directory accordingly (encrypted/offline storage; restricted access and sharing). Avoid uploading these files to issue trackers or attaching them to diagnostic logs. Treat accidentally exposed copies as potential exposure of credentials formerly stored within. Do not assume deleting the live source removes its information from historical recovery files.

Broadcaster intentionally does **not** automatically expire, compact or delete these historical recovery copies. If you need to handle them manually, stop *all* running Broadcaster instances, verify a separate working backup and the state of the migrated database, and distinguish historical `-v*-recovery-` copies from the active database, D1 recovery/marker/staging files and user exports. **Deleting a historical snapshot permanently forfeits that snapshot's recovery usefulness.** Never delete files you cannot identify. Deletion is not a guarantee of secure erasure on SSDs, snapshots or backups. An automated retention policy or in-app deletion action would require a separate explicit product/privacy decision.

## EPG staging and disk space

XMLTV imports stage downloaded or selected-guide bytes in the same private directory as `.epg-<UUID>.part`; the attempt cleans up its own file on normal success, failure or cancellation. Hard termination can leave a spool behind. On Linux, Broadcaster performs a **one-time bounded, best-effort orphan sweep** when the guide service starts, after private storage has initialized. A spool must be at least **48 hours old**, have the exact internal v4 UUID name, be a regular owner-owned file, and have a matching regular `.epg-<UUID>.lock` with a *released* kernel lock. Active attempts hold this lock through parsing, including when two application instances overlap. No more than 256 directory entries are inspected and 32 spools removed per pass. Old-version spools without a lock remain untouched rather than risk deleting another instance's live download. There is no background disk purge; manually investigate persistent unusual growth after closing Broadcaster.

**Limits are not a total-disk quota.** Individual staging caps are 2 GiB for uncompressed and 256 MiB for gzip downloads, and the EPG database import guard checks **main SQLite database plus `-wal`** against 6 GiB. The parser also restricts its SQLite temporary-page budget to 128 MiB. These figures do **not** include rollback `-journal` files, other SQLite temporary files, migration recovery snapshots, user-created backups, download spool bytes, unrelated application files or filesystem overhead. Two refreshes or old recovery files can require additional temporary capacity. SQLite connections enable foreign keys, but do not require WAL mode; rollback journaling is possible. Disk-headroom probes may decline imports before filling a filesystem, but cannot promise a maximum total allocation.

Deleting a guide or old programmes frees SQLite pages for reuse but may **not** shrink the database file. This is expected SQLite behavior; a high `freelist_count` is not proof that deletion failed. Broadcaster does not automatically `VACUUM` or silently change journal modes. Before investigating disk pressure, stop imports and measure the private data directory and available free space *locally*, without sharing its secret-bearing filenames. Do not delete active `-wal`, `-journal`, staged D1 import files or migration recovery files to reclaim space.

See [reproducible synthetic SQLite v5 measurements](epg-sqlite-benchmark.md) for measured disk use and timing limitations.
